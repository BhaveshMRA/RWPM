653## Simplification Mode（輕量模式）
654 
655Use when code is hard to read but **structure is sound** — improve namin
>g, reduce cognitive load, and inline redundancy. Do NOT reshape structur 
>e or add new logic. 
656 
657**Difference from Structural Refactor**:
658 
659| Structural Refactor | Simplification Mode |
660|---------------------|---------------------|
661| Extract functions, decompose classes | Rename variables, inline trivia
>l helpers | 
662| Change call hierarchies | Improve comments, remove noise |
663| Apply design patterns | Reorder code within a function |

665### Chesterton's Fence Principle
666 
667> Before removing any code, you MUST understand why it exists. If you do
>n't know why it's there, don't remove it. 
668 
669Steps to apply:
6701. Read the code — understand the original intent
6712. Check git history (`git log -p`) for context
6723. Search for callers or side effects that might not be obvious
6734. Only then decide: simplify, document, or leave it
674 
675### Rule of 500
676 
677If a single function exceeds **500 lines**: do NOT attempt crude deletio
>n. Use automated refactoring tools (IDE rename/extract, `rope` for Pytho 
>n, Roslyn for C#) to split safely. 
678

680

6821. Add minimal coverage first (`happy path` + `error path`)
6832. Confirm tests pass (Green)

723## Common Rationalizations
724 
725在執行重構過程中，AI 可能以下列藉口跨越重構範疇：
726 
727| 常見藉口 | 反制說明 |
728|---------|---------|
729| "順手加個 feature 不會怎樣" | ⛔ 重構 = 純行為保留的結構改善——任何新功能或行為變更必須在獨立的 commit 中完成；「
>順手」是最常見的 scope creep 起點 | 
730| "這段程式碼看起來沒用，直接刪掉比較乾淨" | Chesterton's Fence 原則——移除任何程式碼前必須先理解「為何有這段」；未理
>解其存在原因之前，不得刪除 | 
731| "這個迴圈明顯可以優化，我直接改就好" | 無量測基線的效能優化是猜測而非工程——必須先有 profiler 或 benchmark 數據，
>才能動效能相關的程式碼 | 
732| "沒有測試，所以我知道不會有回歸" | 無測試 = 無安全網——若無測試存在，重構前必須先加對應覆蓋；不得以「程式碼很簡單」替代測試保護 |
733
