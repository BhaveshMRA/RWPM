99## Test Design Principles
100 
101### What to Test
102- **Public interface** - Test behavior users depend on
103- **Edge cases** - Boundaries, empty inputs, max values
104- **Error conditions** - Invalid inputs, exceptions
105- **Business logic** - Core algorithms and rules
106- **Integration points** - Where components interact
107 
108### What NOT to Test
109- **Private implementation details** - Test behavior, not internals
110- **Third-party libraries** - Trust they work, test your usage
111- **Simple getters/setters** - Unless they have logic
112- **Framework code** - Test your code, not the framework
113 
114### One Behavior Per Test
115- Each test should verify single behavior
116- Makes failures easier to diagnose
117- Keeps tests focused and readable
118- Prefer multiple small tests over one large test
119 
120### Make Tests Readable
121- **Descriptive names** - `test_add_returns_sum_of_two_positive_numbers`
122- **Clear structure** - AAA or Given-When-Then
123- **Self-documenting** - Test shows how code should be used
124- **Minimal setup** - Only what's needed for this test
125 
126### Keep Tests Independent
127- Tests should not depend on each other
128- Tests can run in any order
129- Each test starts with clean state
130- No shared mutable state between tests

207

227## Mocking and Test Doubles
228 
229### When to Mock
230- **External dependencies** - Databases, APIs, file systems
231- **Slow operations** - Network calls, large computations
232- **Unpredictable behavior** - Random, time-dependent, external state
233- **Hard to trigger scenarios** - Error conditions, edge cases
234 
235### When NOT to Mock
236- **Your own code** - Prefer real objects for your code
237- **Simple objects** - Data classes, value objects
238- **Logic being tested** - Don't mock what you're testing
239 
240### Types of Test Doubles
241 
242**Mock** - Programmed with expectations, verifies interactions
243**Stub** - Provides canned responses, doesn't verify
244**Fake** - Working implementation, simpler than real
245**Spy** - Records calls, allows verification after
246 
247See `references/test-design-patterns.md` for detailed mocking strategies
 >.

249## Common TDD Anti-Patterns
250 
251**Don't:**
252 
253❌ **Write implementation before test** - Defeats TDD purpose
254 
255❌ **Write multiple tests before making them pass** - Stay in rhythm (one
 > test, make it pass, next test)
256 
257❌ **Refactor with red tests** - Only refactor when green
258 
259❌ **Test implementation details** - Test behavior, not internals
260 
261❌ **Skip refactor step** - Technical debt accumulates
262 
263❌ **Write tests that are hard to understand** - Tests are documentation
264 
265❌ **Create dependencies between tests** - Tests must be independent
266 
267❌ **Mock everything** - Use real objects when practical
268 
269❌ **Fake it with hardcoded values forever** - "Fake it till you make it"
 > is temporary
270 
271❌ **Write slow tests** - Slow test suite won't be run frequently
