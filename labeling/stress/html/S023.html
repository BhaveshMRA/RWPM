16## TTL 策略（Crucial）
17 
18- **每個快取 Key 都必須設定 TTL**，禁止無期限快取（配置類長效資料也應設長 TTL 而非永久）。

22## 快取模式
23 
24- **預設 Cache-Aside**：讀取先查快取，未命中查資料來源後回填。寫入時**失效（刪除）對應 Key**，不採「寫入時更新快取值」
 >（雙寫易產生不一致）。
25- 高併發熱點 Key 的回源需防擊穿：優先使用 .NET 9+ 的 `HybridCache`（內建 stampede 防護與 L1/L2 兩
 >層）；未使用 HybridCache 時以 per-key 鎖或單飛（single-flight）模式限制同時回源數。
26- **穿透防護**：查無資料的結果以短 TTL（如 30〜60 秒）快取空值標記，避免不存在的 ID 反覆打穿到資料庫。

28## 失效容錯（Crucial）
29 
30- 快取故障不得中斷業務：連線失敗或逾時時記錄警告並直接回源，**禁止**把 Redis 例外往上拋成 5xx。
31- 回源路徑必須獨立可用，不得存在「只有快取有、資料來源沒有」的資料。

109## Rules
110- Always set TTL (SETEX not SET) — never let keys grow forever
111- Use pipelines for multiple operations (reduces round trips)
112- Key names must be namespaced: `user:123`, not just `123`
113- Use SCAN not KEYS in production (KEYS blocks Redis)
114- Monitor memory: set maxmemory and maxmemory-policy in redis.conf
115- For distributed locks: use Redlock algorithm, not simple SET NX
