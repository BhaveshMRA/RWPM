30## CRITICAL: AskUserQuestion 턴 분리 규칙
31 
32**AskUserQuestion은 이 스킬이 로드된 턴(같은 assistant turn)에서 절대 호출하지 마세요.**
33 
34Skill tool로 이 스킬이 로드되면, 같은 턴에서 AskUserQuestion을 호출할 경우 사용자에게 질문 UI가 표시되지
 > 않고 빈 응답으로 자동 처리됩니다 (Claude Code 플랫폼 제약).
35 
36**필수 절차:**
371. Phase 1 (Input 분석 + 정보 맵핑)을 수행한다
382. 정보 맵핑 결과를 **텍스트로 출력**한다
393. **반드시 STOP하고 사용자 응답을 기다린다**
404. 사용자가 응답한 **다음 턴**에서 AskUserQuestion으로 Phase 1.5/3을 시작한다
41 
42이 규칙을 어기면 사용자가 질문을 볼 수 없고, 확인 절차가 진행되지 않습니다.
43 
44## 핵심 원칙
45 
46**1. 비기술 언어 유지.**
47기획팀이 읽고 확인할 수 있는 언어로 작성한다. 개발 용어 사용 금지.
48 
49**2. [추정]은 반드시 표시한다.**
50AI가 도메인 지식으로 채운 내용에는 `[추정]` 마크를 붙인다. 사용자가 확인하지 않은 추정은 spec-reviewer가 검출할
 > 수 있게 유지한다.
51 
52**3. 없는 정보를 만들어내지 않는다.**
53추정 가능한 범위(도메인 상식)는 [추정]으로 채우되, 비즈니스 결정이 필요한 항목은 빈칸으로 두고 사용자에게 질문한다.
54 
55**비즈니스 결정 vs 도메인 상식 구분 기준:**
56 
57| 도메인 상식 ([추정] 가능) | 비즈니스 결정 (질문 필수) |
58|---|---|
59| 업계 표준 UX 패턴 (좋아요 토글, 목록 페이지네이션) | 수익/과금 관련 결정 |
60| 일반적 데이터 구조 (생성일시, 수정일시 필드) | 정책/규칙 (본인 글 좋아요 허용 여부) |
61| 보편적 예외 (네트워크 오류, 중복 요청) | 브랜딩/톤 관련 결정 |
62| 기본 권한 구조 (로그인 필요 여부) | 범위 결정 (v1에 뭘 넣을지) |
63| 표준 상태 흐름 (읽음/안읽음) | 알림/연동 대상 결정 |
64| 기본 장애 응답 (재시도 안내 메시지, 오류 표시) | 장애 복구 정책 (재시도 횟수, 폴백 동작, 보상 처리) |
65 
66## Protocol
67 
68> **Input 유형 판단은 Phase 1 시작 전에 수행한다.** 사용자가 input을 제공했는지 먼저 확인하고, 없으면 "어
 >떤 기능의 기획서를 작성할까요?"를 텍스트로 출력한 뒤 STOP한다. 사용자의 다음 턴 응답을 받은 후 Phase 1로 진입한다.

70### Phase 1: Input 분석
71 
721. **요구사항 파일 확인**:
73   - `specs/{feature}-requirements.md` 존재 여부 확인 (Glob)
74   - 같은 세션에서 spec-interview가 실행되었다면 해당 컨텍스트 활용
75   - 사용자가 직접 제공한 텍스트/파일도 가능
76   - 요구사항 파일이 없고 텍스트만 제공된 경우, slug는 사용자에게 "이 기능의 영문 이름을 정해주세요 (예: user-l
 >ike, notification)" 로 확인
77 
782. **기존 관련 문서 스캔**:
79   - `specs/` 폴더에서 관련 기능의 기존 기획서/요구사항 스캔 (Glob/Read)
80   - 중복이나 의존 관계 파악
81 
823. **정보 맵핑**:
83   요구사항에서 7개 섹션에 매핑 가능한 정보를 분류:
84 
85   | 섹션 | 정보 있음 | 정보 없음 (채워야 함) |
86   |------|----------|---------------------|
87 
88   이 매핑 결과를 사용자에게 간략히 공유한다:
89   "요구사항에서 [N개 섹션]은 충분히 커버됩니다. [M개 섹션]은 추정으로 채우거나 확인이 필요합니다."

91### Phase 1.5: 미결 사항 처리
92 
93요구사항에 "미결 사항"이 있는 경우, Phase 2 진입 전에 처리한다:
94- 각 미결 사항에 대해 AskUserQuestion: "요구사항에서 미결이었던 [항목]은 결정되었나요?"
95- 결정됨 → 해당 섹션에 반영
96- 여전히 미결 → 기획서 하단 "미결 사항" 섹션에 명시적으로 기록하고, 해당 섹션은 빈칸으로 둔다 ([추정]으로 채우지 않는다
 >)
97- 처리 후에도 미결로 남은 항목이 3개 이상이면 "spec-interview 재실행을 권장합니다" 안내
98 
99### Phase 2: 초안 생성
100 
1017개 섹션을 순서대로 채운다. 각 섹션의 작성 규칙:
102 
103**섹션 1. 배경**
104- 요구사항의 "배경" 또는 문맥에서 추출
105- 현재 문제와 해결 필요성을 1-2문단으로
106 
107**섹션 2. 사용자와 목표**
108- 사용자 유형별 목표와 주요 행동을 표로 정리
109- 요구사항에서 명시적으로 나오지 않은 사용자 유형이 있으면 [추정]으로 추가
110 
111**섹션 3. 사용 시나리오**
112- **정상 흐름**: 단계별로 "사용자가 ~ 한다 → 시스템이 ~ 한다" 형태
113- **예외 상황**: 표 형태 (상황 | 사용자에게 보이는 것 | 시스템 동작)
114- 요구사항에서 예외가 없으면 도메인 기반으로 [추정] 예외 추가
115 
116**섹션 4. 데이터와 상태**
117- **주요 데이터**: 항목 | 설명 | 필수 여부 | 제약
118- **상태 변화**: 현재 상태 | 이벤트 | 다음 상태 | 부수 효과
119- spec-interview가 **발견한** 상태와 전이를 **표로 구조화**하는 것이 이 섹션의 역할이다. 누락된 조합의 완전
 >성 검증은 spec-reviewer가 수행한다.
120- 해당하지 않으면 "상태 변화 없음" 명시
121 
122**섹션 5. 연결되는 시스템**
123- 시스템 | 연동 내용 | 방향 (보내기/받기/양방향)
124- 해당하지 않으면 "외부 연동 없음" 명시
125 
126**섹션 6. 권한**
127- 역할 | 할 수 있는 것 | 할 수 없는 것
128- 요구사항에서 역할이 언급되지 않았으면 [추정]으로 기본 역할 추가
129 
130**섹션 7. 범위와 성공 기준**
131- 이번에 하는 것 / 안 하는 것 / 성공 기준
132- 성공 기준은 가능한 한 테스트 가능한 형태로
133- **비기능 요구사항**: 동시 사용자 수, 기대 반응 속도, 보안/개인정보 등 interview에서 수집된 NFR을 이 섹션 
 >하위에 기록
134- 해당하지 않으면 "비기능 요구사항 없음" 명시

136### Phase 3: 사용자 확인
137

 >래도 진행하면 Phase 3 진행하되, 출력 파일에 "요구사항 보완 필요" 경고 표시 |
