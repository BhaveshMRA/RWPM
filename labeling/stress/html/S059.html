105## Index Patterns
106 
107### 1. Add Indexes on WHERE and JOIN Columns
108 
109**Impact:** 100-1000x faster queries on large tables
110 
111```sql
112-- ❌ BAD: No index on foreign key
113CREATE TABLE orders (
114  id bigint PRIMARY KEY,
115  customer_id bigint REFERENCES customers(id)
116  -- Missing index!
117);
118 
119-- ✅ GOOD: Index on foreign key
120CREATE TABLE orders (
121  id bigint PRIMARY KEY,
122  customer_id bigint REFERENCES customers(id)
123);
124CREATE INDEX orders_customer_id_idx ON orders (customer_id);
125```
126 
127### 2. Choose the Right Index Type
128 
129| Index Type | Use Case | Operators |
130|------------|----------|-----------|
131| **B-tree** (default) | Equality, range | `=`, `<`, `>`, `BETWEEN`, `IN
>` | 
132| **GIN** | Arrays, JSONB, full-text | `@>`, `?`, `?&`, `?|`, `@@` |
133| **BRIN** | Large time-series tables | Range queries on sorted data |
134| **Hash** | Equality only | `=` (marginally faster than B-tree) |
135 
136```sql
137-- ❌ BAD: B-tree for JSONB containment
138CREATE INDEX products_attrs_idx ON products (attributes);
139SELECT * FROM products WHERE attributes @> '{"color": "red"}';
140 
141-- ✅ GOOD: GIN for JSONB
142CREATE INDEX products_attrs_idx ON products USING gin (attributes);
143```
144 
145### 3. Composite Indexes for Multi-Column Queries
146 
147**Impact:** 5-10x faster multi-column queries
148 
149```sql
150-- ❌ BAD: Separate indexes
151CREATE INDEX orders_status_idx ON orders (status);
152CREATE INDEX orders_created_idx ON orders (created_at);
153 
154-- ✅ GOOD: Composite index (equality columns first, then range)
155CREATE INDEX orders_status_created_idx ON orders (status, created_at);
156```
157 
158**Leftmost Prefix Rule:**
159- Index `(status, created_at)` works for:
160  - `WHERE status = 'pending'`
161  - `WHERE status = 'pending' AND created_at > '2024-01-01'`
162- Does NOT work for:
163  - `WHERE created_at > '2024-01-01'` alone
164 
165### 4. Covering Indexes (Index-Only Scans)
166 
167**Impact:** 2-5x faster queries by avoiding table lookups
168 
169```sql
170-- ❌ BAD: Must fetch name from table
171CREATE INDEX users_email_idx ON users (email);
172SELECT email, name FROM users WHERE email = 'user@example.com';
173 
174-- ✅ GOOD: All columns in index
175CREATE INDEX users_email_idx ON users (email) INCLUDE (name, created_at)
>; 
176```
177 
178### 5. Partial Indexes for Filtered Queries
179 
180**Impact:** 5-20x smaller indexes, faster writes and queries
181 
182```sql
183-- ❌ BAD: Full index includes deleted rows
184CREATE INDEX users_email_idx ON users (email);
185 
186-- ✅ GOOD: Partial index excludes deleted rows
187CREATE INDEX users_active_email_idx ON users (email) WHERE deleted_at IS
> NULL; 
188```
189 
190**Common Patterns:**
191- Soft deletes: `WHERE deleted_at IS NULL`
192- Status filters: `WHERE status = 'pending'`
193- Non-null values: `WHERE sku IS NOT NULL`

277## Security & Row Level Security (RLS)
278 
279### 1. Enable RLS for Multi-Tenant Data
280 
281**Impact:** CRITICAL - Database-enforced tenant isolation
282 
283```sql
284-- ❌ BAD: Application-only filtering
285SELECT * FROM orders WHERE user_id = $current_user_id;
286-- Bug means all orders exposed!
287 
288-- ✅ GOOD: Database-enforced RLS
289ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
290ALTER TABLE orders FORCE ROW LEVEL SECURITY;
291 
292CREATE POLICY orders_user_policy ON orders
293  FOR ALL
294  USING (user_id = current_setting('app.current_user_id')::bigint);
295 
296-- Supabase pattern
297CREATE POLICY orders_user_policy ON orders
298  FOR ALL
299  TO authenticated
300  USING (user_id = auth.uid());
301```
302 
303### 2. Optimize RLS Policies
304 
305**Impact:** 5-10x faster RLS queries
306 
307```sql
308-- ❌ BAD: Function called per row
309CREATE POLICY orders_policy ON orders
310  USING (auth.uid() = user_id);  -- Called 1M times for 1M rows!
311 
312-- ✅ GOOD: Wrap in SELECT (cached, called once)
313CREATE POLICY orders_policy ON orders
314  USING ((SELECT auth.uid()) = user_id);  -- 100x faster
315 
316-- Always index RLS policy columns
317CREATE INDEX orders_user_id_idx ON orders (user_id);
318```

320### 3. Least Privilege Access
321 
322```sql
323-- ❌ BAD: Overly permissive
324GRANT ALL PRIVILEGES ON ALL TABLES TO app_user;

326-- ✅ GOOD: Minimal permissions
327CREATE ROLE app_readonly NOLOGIN;

373## Concurrency & Locking
374 
375### 1. Keep Transactions Short
376 
377```sql
378-- ❌ BAD: Lock held during external API call
379BEGIN;
380SELECT * FROM orders WHERE id = 1 FOR UPDATE;
381-- HTTP call takes 5 seconds...
382UPDATE orders SET status = 'paid' WHERE id = 1;
383COMMIT;
384 
385-- ✅ GOOD: Minimal lock duration
386-- Do API call first, OUTSIDE transaction
387BEGIN;
388UPDATE orders SET status = 'paid', payment_id = $1
389WHERE id = $2 AND status = 'pending'
390RETURNING *;
391COMMIT;  -- Lock held for milliseconds
392```
393 
394### 2. Prevent Deadlocks
395 
396```sql
397-- ❌ BAD: Inconsistent lock order causes deadlock
398-- Transaction A: locks row 1, then row 2
399-- Transaction B: locks row 2, then row 1
400-- DEADLOCK!
401 
402-- ✅ GOOD: Consistent lock order
403BEGIN;
404SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
405-- Now both rows locked, update in any order
406UPDATE accounts SET balance = balance - 100 WHERE id = 1;
407UPDATE accounts SET balance = balance + 100 WHERE id = 2;
408COMMIT;
409```
410 
411### 3. Use SKIP LOCKED for Queues
412 
413**Impact:** 10x throughput for worker queues
414 
415```sql
416-- ❌ BAD: Workers wait for each other
417SELECT * FROM jobs WHERE status = 'pending' LIMIT 1 FOR UPDATE;
418 
419-- ✅ GOOD: Workers skip locked rows
420UPDATE jobs
421SET status = 'processing', worker_id = $1, started_at = now()
422WHERE id = (
423  SELECT id FROM jobs
424  WHERE status = 'pending'
425  ORDER BY created_at
426  LIMIT 1
427  FOR UPDATE SKIP LOCKED
428)
429RETURNING *;
430```

491### 4. UPSERT for Insert-or-Update
492 
493```sql

496-- Both threads find nothing, both insert, one fails
497

499INSERT INTO settings (user_id, key, value)
500VALUES (123, 'theme', 'dark')
501ON CONFLICT (user_id, key)
502DO UPDATE SET value = EXCLUDED.value, updated_at = now()
503RETURNING *;
