201## Why Order Matters
202 
203**"I'll write tests after to verify it works"**
204 
205Tests written after code pass immediately. Passing immediately proves no
 >thing:
206- Might test wrong thing
207- Might test implementation, not behavior
208- Might miss edge cases you forgot
209- You never saw it catch the bug
210 
211Test-first forces you to see the test fail, proving it actually tests so
 >mething.
212 
213**"I already manually tested all the edge cases"**
214 
215Manual testing is ad-hoc. You think you tested everything but:
216- No record of what you tested
217- Can't re-run when code changes
218- Easy to forget cases under pressure
219- "It worked when I tried it" ≠ comprehensive
220 
221Automated tests are systematic. They run the same way every time.
222 
223**"Deleting X hours of work is wasteful"**
224 
225Sunk cost fallacy. The time is already gone. Your choice now:
226- Delete and rewrite with TDD (X more hours, high confidence)
227- Keep it and add tests after (30 min, low confidence, likely bugs)
228 
229The "waste" is keeping code you can't trust. Working code without real t
 >ests is technical debt.
230 
231**"TDD is dogmatic, being pragmatic means adapting"**
232 
233TDD IS pragmatic:
234- Finds bugs before commit (faster than debugging after)
235- Prevents regressions (tests catch breaks immediately)
236- Documents behavior (tests show how to use code)
237- Enables refactoring (change freely, tests catch breaks)
238 
239"Pragmatic" shortcuts = debugging in production = slower.
240 
241**"Tests after achieve the same goals - it's spirit not ritual"**
242 
243No. Tests-after answer "What does this do?" Tests-first answer "What sho
 >uld this do?"
244 
245Tests-after are biased by your implementation. You test what you built, 
 >not what's required. You verify remembered edge cases, not discovered on
 >es.
246 
247Tests-first force edge case discovery before implementing. Tests-after v
 >erify you remembered everything (you didn't).
248
